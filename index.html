Real-time computational fluid dynamics

The fluid is real.

Every frame, your GPU advects a velocity field through itself, measures its divergence, solves a Poisson equation for pressure, and subtracts the gradient to make the flow incompressible. Twenty-two iterations. Thirty passes. Eleven milliseconds on the M1 this was built on. Then it does it again.

01 — The method

Stable fluids, unchanged since 1999.

Jos Stam's insight was that you can take an arbitrarily large timestep without the simulation exploding, if you stop trying to push particles forward and instead ask each cell where its contents came from. Trace the velocity field backwards, sample what was there, done. Unconditionally stable.

The price is that it is a first-order scheme, so it bleeds energy — vortices that should persist for minutes flatten out in seconds. The fix is to measure the curl that was lost and push it back in. That is the Vorticity slider below. Turn it past forty and the fluid starts to boil, because you are now adding more rotation than the physics removed.

  1. curl measure rotation across the grid
  2. vorticity re-inject what advection smeared away
  3. divergence find where fluid is compressing
  4. pressure ×22 Jacobi sweeps of the Poisson solve
  5. gradient subtract pressure — flow is now incompressible
  6. advect move velocity through itself, then the ink through it
02 — Instruments

Numbers measured, not claimed.

Read from the running system: frame time from the render clock, grid sizes and memory from the allocated textures, the renderer string from your driver. If the fluid stutters, this readout will say so.

03 — Controls

Break it on purpose.

These are the actual solver parameters, not a theme picker. Drop the Jacobi sweeps to 1 and watch the fluid lose its ability to know about the far side of the screen; the ink will visibly pile up instead of flowing around.

04 — Colophon

What this is, honestly.

One HTML file, one stylesheet, eleven ES modules, nine GLSL programs. No framework, no bundler, no CDN, no analytics, nothing phoning home. It runs from a static directory and it runs offline.

The ink colour is not random. Speed is mapped through a saturating curve into a five-stop ramp that runs indigo → teal → amber → white, so the bright cores are literally where you moved fastest. A random hue per stroke would have been easier and would have read as a rainbow smear.

Built as an introduction, by Super Dev.
Tested: 60 unit tests over the solver's pure logic, plus 11 headless-browser checks that read pixels back off the GPU to prove it actually paints. Three real bugs were found that way, including a splat radius that was squared when it should not have been.
